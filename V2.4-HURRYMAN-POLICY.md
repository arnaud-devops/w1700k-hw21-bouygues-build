# W1700K HW2.1 Bouygues custom v2.4 policy

This document freezes the source and runtime policy for the v2.4 candidate.
The target is one W1700K HW2.1 used as a routed Bouygues/B&You gateway:

- UBI2 board profile `gemtek,w1700k-ubi`;
- Airoha AN7581 target;
- RTL8261CE on WAN and LAN2;
- DHCP WAN on VLAN 100;
- routed DHCPv6-PD `/60`, without NAT6;
- full dual-stack PPE offload;
- three independent 2.4, 5 and 6 GHz APs in the normal configuration.

Building this image does not authorize a router flash. Until the hardware gate
passes, every v2.4 release must remain marked:

```text
[UNTESTED ON HW2.1 - DO NOT FLASH YET]
```

## Source baseline

The source is Hurryman's immutable 25 July branch and commit:

```text
Repository: https://github.com/hurryman2212/OpenW1700k-test
Branch: ubi2-oc-offload
Commit: 2d02d62666bd8f6ef89b193238c58984db592330
Version: r35578-2d02d62666
```

This is source-built. The published Hurryman firmware is not repacked.

The choice was rechecked on 26 July 2026:

- Hurryman's latest branch head is still the exact pinned commit;
- Fanboy's latest UBI2 is `r35571`, seven OpenWrt revisions older;
- Gilly's new clean image is `r0+35551-ec8f8db38e`;
- Gilly's later `debug+guard` artifact publishes no corresponding source
  change. Its FIT kernel and DTB are byte-identical to the clean image; only
  the rootfs MT7996 module and APK metadata differ. It contains a diagnostic
  three-link MLO remap guard and is not a clean source baseline;
- OpenWrt PR 24038 remains open, unchanged and in draft.

The v2.4 source therefore remains the most recent inspectable W1700K baseline
among these candidates.

## Kernel, hostapd and mt76

The candidate uses:

```text
Linux: 6.18.39
hostapd: 2026-07-09, f08f2749aa696c4e47c5c0f591dda99951bf9fac
mt76: 2026-07-01, 59676919ea408b0b13a9d23f2e2e1a1ab407fba1
```

Linux 6.18.40 was released upstream on 24 July. It is deliberately not
substituted into this candidate: OpenWrt `main`, Hurryman, Fanboy and Gilly
still use 6.18.39, and the full Airoha patch stack has not been rebased and
validated on 6.18.40. The newest upstream number is not preferable to the
newest integrated OpenWrt kernel for a hardware-test candidate.

The hostapd and mt76 pins match OpenWrt `main` as checked on 26 July. Hurryman's
MLO VLAN binding correction and MT7996 malformed PS-sync TLV protection remain
in the source. Gilly's radar `chanctx` attribution correction is overlaid and
checksum-locked.

## IPv6 UPDMEM policy

The normal dual-stack fw4 rule remains active:

```text
meta l4proto { tcp, udp } flow offload @ft;
```

Applied:

- patch `972`, which writes the actual IPv6 egress source MAC into UPDMEM;
- patch `973` v3, which allocates refcounted UPDMEM slots per distinct source
  MAC and falls back only the affected flow when no slot is safe.

Forbidden:

- old single-slot patch `971`;
- selective software-fallback patch `965`.

Applying `965` would prevent the WAN-uplink flow from reaching the allocator
and would therefore mask the hardware validation of `972+973`.

Patch `973` is intentionally experimental. Compilation and offline inspection
cannot validate slot lifetime, refcounts or concurrent flow teardown on real
PPE hardware. Those are explicit hardware-test gates, not claims made by the
build.

## Bridge offload policy

The Hurryman kernel contains the reviewed bridge-flow series needed for a
future controlled L2 test:

- generic patches `675-01` through `675-05`;
- flow teardown patches `700` and `701`;
- W1700K reassociation and teardown patches `990-01`, `990-02` and `9990`;
- mac80211 switchdev FDB deletion on station disconnect.

The crude unconditional Hurryman userspace service is removed. It is replaced
with fw4 integration derived from the architecture of PR 24038, but with an
independent option:

```text
firewall.@defaults[0].flow_offloading_bridge='0'
```

This option defaults to disabled. Routed dual-stack offload remains enabled.
The bridge path can therefore be tested separately without changing the first
boot baseline.

The image does not install:

- `bridge-flow-offload`;
- `kmod-br-netfilter`;
- `bridger`;
- PR 24038 as an undifferentiated patch stack.

## Airoha experimental code removed

The exact 46-patch Hurryman SOE/XFRM/LAG experiment and its mt76 patch `9993`
companion are verified by SHA-256 and then removed. Patch `9993` calls the
flowtable-context API introduced by experimental patch `9999-25`; retaining
one without the other is invalid. With the SOE provider absent, mt76 keeps its
established callback for both TC and flowtable setup. The Airoha Ethernet
package no longer forces `NET_AIROHA_SOE=y` or `kmod-ipsec4-offload`.

This does not remove normal routed PPE, Wi-Fi WED, EIP93 or the reviewed bridge
path. It removes an unrelated inline IPsec and bonding experiment from the
kernel surface to be tested on this DHCP/VLAN gateway.

Hurryman's automatic overclock and performance governor are also removed:

- maximum CPU OPP: 1.2 GHz;
- default governor: `ondemand`;
- no automatic PLL overclock.

Hardware GRO/LRO support remains compiled, but hardware LRO is disabled in the
initial netdev feature set. It can be tested explicitly later.

## RTL8261CE policy

The CE-specific driver is retained because it is the path already validated on
this W1700K HW2.1, including the board's SerDes/polarity requirements.

The bind callback is hardened to require all three conditions:

1. Clause 45 PHY;
2. the generic Realtek vendor/model match;
3. the CE PMA/PMD model value.

This prevents the CE driver from claiming the sibling RTL8261N while avoiding
the Generic Clause 45 fallback previously observed on HW2.1.

OpenWrt PR 23644 remains open. Its upstream-oriented Realtek driver is useful
for the eventual mainline solution, but it has not replaced the currently
validated CE-specific W1700K2 path.

## Firmware and Wi-Fi policy

The image keeps the Hurryman NPU and MT7996 firmware selected by the pinned
source. CI verifies that the assembled rootfs contains:

- both Airoha EN7581 MT7996 NPU firmware blobs;
- MT7996 ROM patch, WM, WA and DSP firmware;
- RTL8261 firmware;
- one native `mt7996e` module;
- one native RTL8261CE module.

Full `wpad-openssl` is mandatory. All basic and mbedTLS wpad variants are
rejected, preventing the preserved 802.11k/v settings from suppressing all
three APs after sysupgrade.

MLO support and its LuCI panel are present, but MLO remains disabled in the
normal configuration. The opaque Gilly three-link debug module is not included.

## Native kmod repository

The image no longer forces Fanboy's official buildbot vermagic.

Instead:

- the kernel uses its native vermagic;
- `CONFIG_ALL_KMODS=y` builds the matching module packages;
- the release publishes all native `kernel-*` and `kmod-*` APKs;
- the repository index is signed by the image's ephemeral APK key;
- the public key, repository checksums, index JSON and ABI metadata are release
  assets;
- the exact release-specific repository URL is embedded in the image;
- the public OpenWrt kmods feed is removed.

This means every buildable kmod exposed by the enabled core and feed metadata,
not every third-party module in the OpenWrt ecosystem. The sole explicit
exception is the unrelated Telephony `kmod-ipt-rtpengine`: its required source
header is absent from this Linux 6.18 feed combination. It is disabled rather
than weakening the kernel or feed pins to make an unused module compile.

This removes the ABI ambiguity of installing official kmods against a patched
kernel. The package signature authenticates the repository; it does not turn
an untested kernel module into a supported runtime feature.

The repository key and URL are preserved through sysupgrade under unique names.
Kernel package dependencies still prevent modules from another kernel ABI from
being installed after a later generic upgrade.

## Administration and recovery

Included:

- full OpenSSL LuCI HTTPS stack;
- `dnsmasq-full` and `dnsproxy`;
- AdGuard Unfiltered DoQ primary, NextDNS DoQ fallback and DNS.SB bootstrap;
- package-managed DoQ and full-wpad sysupgrade recovery;
- Dropbear, OpenSSH SFTP and LAN-only TLS `ttyd`;
- LuCI file manager and APK manager;
- FlowSense 1.1.4-r3 and Airoha NPU panels;
- MLO and Wi-Fi 7 panels;
- Watchcat, irqbalance and pstore/ramoops;
- SQM/Cake, installed but disabled;
- browser nPerf, LibreSpeed and focused network tools.

The following remain disabled by default:

- bridge offload;
- FlowSense external jitter probing;
- LibreSpeed server;
- SQM/Cake;
- MLO;
- packet steering;
- hardware LRO;
- overclocking.

Watchcat only migrates the untouched stock profile. It performs serialized
logical `wan` or `wan6` recovery after a 15-minute failure window and does not
automatically reboot the complete router.

Generic Attended Sysupgrade and `owut` are excluded. The public ASU service
cannot reproduce this source, native kmod repository, patch stack, signing key
or recovery package. Upgrades remain checksum-verified and explicitly
controlled until a compatible custom ASU backend exists.

Ookla's downloaded binary, its RPC downloader and its LuCI view are excluded.
The image retains browser nPerf, `iperf3`, `curl`, `tcpdump` and LibreSpeed
without introducing an unpinned runtime executable.

## Required hardware gate

Offline audit proves structure and provenance, not behavior. A separately
authorized test must cover:

- boot and rollback;
- RTL8261CE binding on WAN and LAN2;
- WAN 10 Gbit/s and multigig LAN2 negotiation;
- sustained IPv4 and IPv6 downloads and uploads with `HW_OFFLOAD`;
- UPDMEM allocation and release under multiple source-MAC flows;
- flow teardown and reconnect without stale entries;
- all three independent APs, DoQ, SFTP and ttyd;
- IRQ distribution and latency with irqbalance;
- pstore capture after a controlled reboot;
- only then, a separate bridge-offload A/B test.

Until these checks pass, v2.4 is a stronger test candidate than the prior
custom images, not a production replacement for the validated Gilly 17.07
router image.
